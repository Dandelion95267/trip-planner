# V3：来源证据与餐饮衔接

实施日期：2026-11-05。基于V2提交2d0bad6继续修改，本页不改写V0/V1/V2历史结果。

## 原问题

1. HTTP评测只得到最终行程，拿不到当时的景点、酒店、餐馆及补坐标依据，candidate_sources为unknown。
2. 原餐馆按全城关键词搜索并提前固定；景点可能因路线修复变化，餐馆与描述未同步。V2真实样例出现“王府井附近用餐”但实际候选为牡丹园店。
3. V2老人单条耗时149.2302秒，需记录阶段开销后再判断瓶颈，不能只增加查询。

## 实施

- source_evidence.py在真实工具返回并解析后复制快照，记录查询参数白名单、UTC时间、候选与地点详情，绑定请求ID。来源不由模型生成。
- amap_service.py接入采集器及官方MCP的maps_around_search。实际读取工具定义确认keywords、location、radius参数，不假设不存在的接口。
- dining_service.py在最终景点路线形成后选餐馆，午餐参考首站、晚餐参考末站，按2000米直线范围粗筛，优先最近的不同餐馆；缺坐标时只有限补详情，无法核验就保留提示而非编造。
- 初次规划不再搜索全城餐馆；同一请求对相同最终景点复用餐馆搜索，景点变化则重新核验。当前每轮餐饮35秒、每请求最多8次搜索/16次新详情；已有详情直接复用，没有追加模型调用。
- 确定餐馆后由最终结构化字段重建每日及总体说明，明确直线距离不是步行距离、接驳/营业/菜单/价格未确认，安排建议休息。缺失餐饮明确显示，不能把省略餐馆当成质量成功。
- schemas.py新增来源、耗时、餐饮诊断和锚点距离。TripPlannerAgent剔除模型输出中的伪造元数据；审核模型不重复接收大体积来源快照，并保持景点间步行约束的原始范围。
- run_eval.py保存新快照；evaluators.py核对请求ID、候选来源成员、名称地址及搜索/详情中的坐标。旧格式和旧记录保持原口径，缺证据仍unknown，矛盾仍failed。
- 前端餐馆卡片、行程复制和PDF显示直线/缺失提示，JSON包含完整元数据。
